## Patterns shared with the other five repositories

1. **"Exactly-once" was at-least-once in both queue repositories** (this one
   and ai-dlh), through the same three gaps: (a) post-claim transitions did not
   check the lock's identity, so a worker whose lock had been reclaimed still
   wrote over the new holder's row; (b) nothing was recorded between the
   external effect and the journal, so a crash or a lost acknowledgement
   produced a duplicate effect; (c) the stale-lock window was not validated
   against real processing time. The fix was the same in both: a lock token on
   every transition, and the honest shape of the guarantee written down.
2. **CI hygiene identical everywhere.** No `permissions:` (6/6), mutable tags
   (6/6). `permissions: contents: read` landed here in PR #5. This repository
   uses only first-party `actions/*`, so there is nothing to SHA-pin.
3. **Documentation asserting what the code did not do.** Here, `README.md:6`
   said "settles exactly once".

## Decision taken by the owner, 2026-09-06

| Topic | Decision | Reasoning |
|---|---|---|
| `Idempotency-Key` is an oracle | Declare in the README that the key is the caller's secret, and replace the `order-1001` example with a UUID. Do not scope the key by caller until there is a caller. | Without authentication, a guessed key with the same body returns a third party's whole payout, and a different body returns 422 confirming existence. Authentication is explicitly out of scope, so scoping by caller would be inventing one. What can be done today is to stop inviting enumeration. |

## Medium and low, apply-only

- [x] The return of `update()` was discarded in all three transitions, so a lost transition was entirely silent. Now logged at WARN (retry, fail) or ERROR (confirm after a successful settlement). PR #6.
- [x] `README.md` and `PayoutRequested` attributed to the Kafka key a guarantee it does not give (the poller does not go through Kafka at all). Corrected. PR #6.
- [ ] The idempotency fingerprint covers only `amount|currency`; a third field added to the record would be silently ignored. Add a structural test that fails when the record gains a field the fingerprint does not know.
- [ ] `Idempotency-Key` has no validated charset and is logged in four places; `CorrelationId` already has the right regex. Apply the same.
- [ ] `handleTypeMismatch` reflects the raw path value into `detail`.
- [ ] `maven-wrapper.properties` has no `distributionSha256Sum`.
- [ ] Migration V2 without `NOT VALID` / `CONCURRENTLY`: a prolonged exclusive lock in production.
- [x] `CLAUDE.md` said the Kafka tests use Testcontainers; only PostgreSQL does, and the failsafe "Skipped" count is reported per module. Corrected. PR #6.
- [ ] No rate limit and no body-size limit on the public `POST /payouts`.

## What holds up

- Secret hygiene is clean in the tree and the history.
- The claim itself was correct all along: a conditional `UPDATE ... RETURNING`,
  never a read-then-write. The problem was everything after the claim, and that
  is now fenced.
- `payout-contracts` is genuinely free of framework code (verified by
  inspecting the compiled classes).
- Errors are closed to the client as a discipline: RFC 7807 everywhere, no
  stack traces, no internal messages.
- The README's "Known limitations" names its gaps before a reviewer finds them.
